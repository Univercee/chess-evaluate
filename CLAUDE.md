# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run dev        # Vite dev server on port 3000 (strictPort, host 0.0.0.0)
npm run build      # Production build
npm run typecheck  # tsc --noEmit — the only automated check
docker-compose up -d   # nginx image serving the build on :8080 (see DOCKER.md)
```

`SITE_URL` (env var, `.env`, or Docker `--build-arg`) is the public site address, e.g. `https://chess.example.com`. The `seo` plugin in `vite.config.js` fills `%SITE_URL%` in `index.html`. It keeps the `SITE_URL:START…END` block (canonical, og:url, hreflang) only when the address is set, and emits `robots.txt` plus, with an address, `sitemap.xml`. Without it the build still works, just without those absolute-URL tags.

**Deployment:** `.github/workflows/deploy-pages.yml` publishes to GitHub Pages on every push to `master` (or manually), at https://univercee.github.io/chess-evaluate/. It builds with `BASE_PATH` (Vite `base`, from `configure-pages`' `base_path`) and `SITE_URL` (its `base_url`). The app is served under a subpath, so never hard-code root paths like `/stockfish/...` in code: use `import.meta.env.BASE_URL` (as `src/engines.ts` does). Absolute paths in `index.html` are rewritten by Vite. When reproducing the build locally in Git Bash, set `MSYS_NO_PATHCONV=1`, otherwise `BASE_PATH=/chess-evaluate/` gets mangled into a Windows path.

There is no test runner and no linter configured. Verify changes with `npm run typecheck`, then check them manually in the browser.

## Architecture

React 18 + TypeScript + Tailwind v4 (via `@tailwindcss/vite`, no config file). Chess rules come from `chess.js`, the board from `react-chessboard` v4, and analysis from Stockfish.

**`src/App.tsx` holds all application state.** There is a single screen: the board plus a sidebar (importer, move list, best lines, New Game). The board is in one of two states:
- **free play** (no `importedGame`): `playMoves` (SAN list) + `playIndex` (how many are shown), with the same `MoveNavigator` as imports. `makeMove` plays from the shown position and drops any moves after it, which is how moves are taken back.
- **imported game**: `importedGame` + `importedMoves` (SAN list) + `currentMoveIndex` + `variation` (the user's own SAN moves played on the board from that index). The displayed `fen` is computed by replaying game moves up to the index and then the variation. It is not stored. While a variation exists, `MoveNavigator` blocks forward navigation and "previous" pops variation moves. `handleMoveChange` always clears the variation.

Layout: from `xl` up it is a 3-column grid, `minmax(0,1fr) auto minmax(18rem,1fr)`, which centers the board and puts the sidebar on the right. Below `xl` the sidebar stacks under the board. `boardWidth` is computed in JS as `clientWidth - 80`, capped at 600: page padding plus the 40px eval bar and 8px gap. From 728px up, a right padding of the same width keeps the board itself centered. Layout changes must keep these numbers in sync.

**Analysis flow:** a `useEffect` in App watches `fen` and calls `analyze(fen, 15, 2000)` after a 100 ms debounce. `position` is a `Chess` instance with the full move history, so threefold repetition counts. When `getGameResult(position)` (`src/gameResult.ts`) reports a finished game, App calls `cancel(fen)` instead: it stops the search and clears the lines. `PrincipalVariations` then shows the result message and `EvaluationBar` shows 1-0 / 0-1 / ½-½ (`result` prop, part of its memo comparison). The resulting `analysis` object drives the `EvaluationBar` and the best-move arrow. The arrow takes the first move of the live best line (`analysis.lines[0]`) while the search runs, and is shown only when `analysis.fen === fen`. When `analyze` is called during a running search, it sends `stop`, waits for that search's `bestmove`, and only then starts the queued search. Keep this: this Stockfish build otherwise delays the stopped search's `bestmove` until after the new search, so the two outputs can't be told apart.

**Engines** (`src/engines.ts`): the user picks one in the Best lines panel (persisted as `engine`). The default is Stockfish 19 Lite (`stockfish-19-lite-single.js`: NNUE, single-threaded, ~550k nps). The legacy option is the original `stockfish.js` (Stockfish 2018, ~45k nps, ~1 s to react to `stop`). Files and sources are in `public/stockfish/README.md`. Both `useStockfish(engine.url)` and `useGameReview(moves, engine.url)` restart their worker when the engine changes, and review caches are keyed per engine.

**`useStockfish`** (`src/hooks/useStockfish.ts`) runs the selected engine as a Web Worker and speaks UCI. It parses `info depth … score cp|mate …` lines and resolves the `analyze` promise on `bestmove`. The engine runs with `MultiPV 3`. Lines are collected per printed batch (`multipv 1..3`) and published together as `analysis.lines`. A batch printed when the time limit cuts an iteration mixes depths and is out of order, so it is dropped (only single-depth batches are published). Grouping per depth instead would drop lines. Only `multipv 1` updates `analysis.score`/`depth`. `analysis.fen` records which position the lines belong to, and `PrincipalVariations` hides lines for any other position. The engine files must exist in `public/stockfish/`, including for Docker builds.

**Game review** (`src/review/`): it doesn't start by itself. `GameReviewPanel` has Start/Stop buttons driving `isReviewRequested` in App, and a game with a cached review (`hasCachedReview`) is shown right away. `useGameReview(importedMoves)` runs a **second** Stockfish worker, separate from the live analysis. It evaluates every position of an imported game with `MultiPV 3` and `go nodes 300000`, after `ucinewgame`. A node budget plus a cleared hash makes results reproducible regardless of CPU load. A time limit (`movetime`) made classifications differ between runs, so don't switch back to it. Finished reviews are cached per game. `classifyMove` (pure) implements the rules from Lichess and Chesskit; both are AGPL, so this is our own code, and **don't paste their code** into this Apache-2.0 project. Win % uses the Lichess formula with cp capped at ±1000. Inaccuracy/mistake/blunder are win-% losses of 5/10/15 (Lichess). Brilliant = piece sacrifice without losing win-%. Only move = alternatives ≥10 win-% worse, not a plain recapture. Excellent/good = losses <2/<5 (Chesskit). When the played move is among the engine lines of the position before it, its value comes from that same search, which avoids adding noise from two short searches. There is no opening book, so no "book" class. Results show in `MoveNavigator` badges, `GameReviewPanel` counts, and as a badge plus square tint on the board for the last game move.

**Score perspective:** Stockfish scores are relative to the **side to move**. `EvaluationBar` flips the sign with `currentMove` (`game.turn()`) to show White-relative values. `EvaluationBar` is memoized to re-render only when `score` changes. That way `currentMove` flipping before the new score arrives does not invert the bar.

**Game import** (`GameImporter`, sidebar): has Chess.com and Lichess tabs. Each platform is a `GameSource` in `src/importers/` that returns months (`fetchArchives`) and normalized `ImportedGameData` per month (`fetchGames`, with an optional cursor for older pages). Only standard-chess games are kept, because the app replays moves from the standard start. Each tab's `SourceBrowser` stays mounted, so its username, lists and per-month cache survive tab switches and game loads. The panel only collapses to a summary. "Import last game" (`importLastGame`) reuses the same machinery. It fetches archives unless they're loaded for that player, walks the newest months (at most `LAST_GAME_MONTHS` = 6, since Lichess months can be empty) through the per-month cache, and loads the first game. The list is left on that month with the game highlighted.
- Chess.com: `chess-web-api` (`getPlayerMonthlyArchives` → `getPlayerCompleteMonthlyArchives`). Type declarations are in `src/types/chess-web-api.d.ts`. Player avatars come from `api.chess.com/pub/player/{username}` (`PlayerBar`, only when `platform === 'chesscom'`). README.md describes an older URL/`getGameByID` flow, which is no longer how it works.
- Lichess: no archive endpoint, so months run from the account's `createdAt` (UTC). Games come from `/api/games/user/{name}` as NDJSON with `since`/`until`, 30 per page, because anonymous exports are throttled to ~20 games/s. The endpoint is wrapped in `NoCrawlers`: it answers **404 to bot-like User-Agents** (curl, HeadlessChrome). When testing with headless browsers, override the UA. 429 means wait a full minute.

## Conventions and gotchas

- **Clone games by replaying history, not by `new Chess(game.fen())`.** Creating a game from a FEN drops the move history and breaks `isThreefoldRepetition()` (see GAME_STATE_HANDLING.md). The `new Chess(game.fen())` snippet in `.clinerules` is outdated on this point.
- Pawn promotion always auto-promotes to a queen.
- Board flip: the effective orientation is `boardFlipped = isFlipped XOR (autoFlip && Black to move)`. `isFlipped` is the button, not persisted and kept across games, but set on import from the searched player's color (`perspective` in `onGameLoad`, compared case-insensitively; unchanged if they aren't in the game); `autoFlip` is the switch, persisted. Use `boardFlipped` for everything visual: besides `boardOrientation`, it swaps the player rows, turns the eval bar over (`flipped` prop, part of its memo comparison) and mirrors the square coordinates used to place the move-class badge. Anything new drawn over the board must account for it.
- Per-browser UI preferences (best-move arrow switch `showBestMoveArrow`, collapsed best lines `bestLinesCollapsed`) use `usePersistentState` (localStorage, with a fallback to plain state). Hiding the arrow or the lines doesn't stop the engine, because the eval bar still needs it. The game review panel is deliberately **not** persisted. It starts expanded on every page load and on every game load (`key={gameLoadId}`).
- **All UI text goes through `t(key)`** from `src/i18n.ts`, in three languages: en, ru and zh. `ru`/`zh` are typed `Record<TranslationKey, string>`, so a key missing in any language fails the typecheck. The language lives in a module-level store: `setLanguage` persists it to localStorage and updates `<html lang>`, the title, meta description, OG/Twitter tags and canonical, plus the URL: `?lang=ru|zh`, none for English. Those URLs are what the hreflang tags and sitemap point to, and `?lang=` wins over the saved choice. The English SEO texts in `index.html` must match the `meta.*` keys. `#root` holds static fallback content for crawlers without JS, which React replaces on mount. `App` subscribes via `useLanguage()`, so the whole tree re-renders on change. A `memo`ized component that renders text must call `useLanguage()` itself. Format dates with `getLocale()`, not `navigator.language`.
- Sidebar panels share one collapsible header: `<h2><button aria-expanded>` with a 16px `ChevronDown` before the title (`-rotate-90` when collapsed), `text-sm text-gray-400`. Keep new panels consistent. The move list collapses but keeps its navigation buttons (needed on touch screens).
- Use chess.js methods for game logic instead of reimplementing rules. Style with Tailwind classes.
- The topic docs in the repo root (`EVALUATION_BAR.md`, `BEST_MOVE_ARROW.md`, `CHESS_COM_IMPORT.md`, `STOCKFISH_SETUP.md`, `DOCKER.md`, `GAME_STATE_HANDLING.md`; some are in Russian) explain individual features in depth. `.clinerules` has a longer description of the architecture.
